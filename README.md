# 🛒 E-Commerce Text-to-SQL Analytics

An AI-powered analytics application that allows users to query an e-commerce database using **natural language**.

Instead of manually writing SQL queries, users can ask questions such as:

> "What are the top 5 best-selling products by revenue?"

The application uses **Google Gemini** to convert the natural-language question into a read-only MySQL query, validates the generated SQL for safety, executes it against the database, and presents the results as an interactive table and visualization.

---

## 🚀 Overview

The project demonstrates how Large Language Models can be integrated with relational databases to create a natural-language analytics interface.

### Traditional workflow

```text
User
 ↓
Understands database schema
 ↓
Writes SQL
 ↓
Executes SQL
 ↓
Analyzes result
```

### This project

```text
User's Natural-Language Question
              ↓
        Google Gemini
              ↓
       SQL Generation
              ↓
        SQL Validation
              ↓
            MySQL
              ↓
       Pandas DataFrame
              ↓
     Table + Visualization
              ↓
        CSV Download
```

The system dynamically introspects the live MySQL schema before generating SQL, allowing Gemini to work with the actual database structure rather than relying solely on a hard-coded schema description.

# 🧠 How the Application Works

## 1. User enters a question

The user enters a question through the Streamlit interface.

Example:

```text
Which 10 customers have spent the most money overall?
```

---

## 2. Application retrieves the database schema

Before asking Gemini to generate SQL, the application inspects the live MySQL database.

It executes:

```sql
SHOW TABLES;
```

and then:

```sql
DESCRIBE `table_name`;
```

This produces a schema description containing:

* table names
* column names
* data types
* primary keys
* foreign keys
* relationships

This schema is included in the Gemini prompt.

### Why?

An LLM cannot reliably generate SQL if it does not know the database structure.

Instead of blindly asking:

```text
"Write SQL for this question."
```

the application provides:

```text
Database Schema
+
User Question
        ↓
      Gemini
```

This significantly reduces the chance of generating nonexistent table or column names.

---

# 🤖 3. Gemini generates SQL

Google Gemini receives:

* the database schema
* the user's question
* SQL-generation rules

The model is instructed to:

* generate exactly one SQL statement
* generate only `SELECT`/`WITH` queries
* use only tables and columns from the supplied schema
* use appropriate joins
* use aggregation when necessary
* use `GROUP BY` where required
* use `ORDER BY` and `LIMIT` for top-N questions
* return only raw SQL

Example:

### User

```text
What are the top 5 best-selling products by revenue?
```

### Gemini

```sql
SELECT
    p.product_name,
    SUM(oi.subtotal) AS total_revenue
FROM products p
JOIN order_items oi
    ON p.product_id = oi.product_id
GROUP BY p.product_id, p.product_name
ORDER BY total_revenue DESC
LIMIT 5
```

---

# 🛡️ 4. SQL Safety Validation

LLM-generated SQL is **never blindly executed**.

The generated query passes through an application-level validation layer.

The validator checks that:

### The query starts with:

```text
SELECT
```

or:

```text
WITH
```

### Multiple statements are rejected

For example:

```sql
SELECT * FROM customers;
DROP TABLE customers;
```

is rejected.

### Destructive keywords are blocked

The application rejects queries containing keywords such as:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
TRUNCATE
CREATE
REPLACE
GRANT
REVOKE
EXEC
EXECUTE
CALL
MERGE
LOCK
UNLOCK
RENAME
SET
```

Therefore, the intended execution path is:

```text
Gemini Output
     ↓
SQL Validator
     ↓
Safe SELECT/WITH query
     ↓
MySQL
```

rather than:

```text
Gemini
 ↓
MySQL
```

This provides an important safety layer when allowing an LLM to generate database queries.

> Note: this is an application-level safety mechanism, not a replacement for proper database permissions. In a production system, the database credentials used by the application should also have read-only privileges.

# 🔍 Why Live Schema Introspection?

A common Text-to-SQL approach is to manually provide a fixed schema to the LLM.

This project goes one step further.

Before generating a query, the application asks MySQL for the current schema:

```sql
SHOW TABLES;
```

and:

```sql
DESCRIBE `table_name`;
```

The resulting schema is then included in the Gemini prompt.

This means the LLM receives information based on the **actual database structure**.

A static schema description is retained as a fallback if the live database cannot be reached.

# 🔐 Security Considerations

The application implements several safeguards.

### 1. API keys are environment variables

The Gemini API key is never hard-coded.

### 2. Generated SQL is validated

The application only allows:

```text
SELECT
WITH
```

queries.

### 3. Multiple SQL statements are rejected

For example:

```sql
SELECT * FROM customers;
DROP TABLE customers;
```

will not be executed.

### 4. Destructive SQL keywords are blocked

Write/DDL operations such as:

```text
INSERT
UPDATE
DELETE
DROP
ALTER
TRUNCATE
CREATE
```

are rejected.

### 5. Production recommendation

For a production deployment, the application should connect to MySQL using a dedicated **read-only database user** rather than a privileged account such as `root`.

# 🧩 Example SQL Generation

### Question

```text
Which customers have spent the most money?
```

Gemini may generate a query similar to:

```sql
SELECT
    CONCAT(c.first_name, ' ', c.last_name) AS customer_name,
    SUM(o.total_amount) AS total_spent
FROM customers c
JOIN orders o
    ON c.customer_id = o.customer_id
GROUP BY c.customer_id, c.first_name, c.last_name
ORDER BY total_spent DESC
LIMIT 10
```

The query is then validated before execution.

# ⚠️ Limitations

This project is designed as an educational AI/data-engineering application.

Current limitations include:

* SQL generation depends on LLM accuracy
* Complex or ambiguous questions may produce incorrect SQL
* The SQL safety layer is application-level validation
* MySQL currently uses a local development setup
* The application does not include authentication
* Query history is maintained only during the current Streamlit session
* The schema is relatively small and designed for demonstration
* No production-scale caching or distributed execution is implemented

# 📚 Key Engineering Insight

The main challenge in a Text-to-SQL system is not simply calling an LLM.

The actual pipeline is:

```text
Natural Language
       ↓
Schema Understanding
       ↓
SQL Generation
       ↓
SQL Validation
       ↓
Database Execution
       ↓
Result Interpretation
       ↓
Visualization
```

Each stage can introduce errors.

This project therefore separates:

1. **LLM reasoning**
2. **SQL safety**
3. **Database execution**
4. **Data presentation**

This separation makes the system easier to understand, debug and extend.
